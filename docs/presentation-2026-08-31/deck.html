Background of the Problem

  • Every server writes a log line for each login, process and network event. A small company produces millions a day; nobody reads them by hand.
  • Security teams use a SIEM (Security Information and Event Management tool — Splunk, Wazuh, QRadar) that matches those lines against written rules.
  • A rule matches text, not meaning. Failed password for root matches; the same event worded differently does not.
  • Recent surveys of log anomaly detection [R2, R7] evaluate on fixed datasets where the attacker is not trying to avoid the detector.

Speaker line: "The tools in use today read the words, not the meaning."

Department of Computer Engineering | SJCEM    3

Background: the evidence

Everything here is our own measurement on real logs, not a claim from a website.

  • Sigma rules: 0 of ~3,300 match an SSH login line. We searched the whole open rule library for Failed password, Accepted password, Invalid user, pam_unix. – No coverage at all for the commonest attack surface on Linux.
  • Wazuh keeps 91% of a brute force — 29% after we reword it. Same attack, same volume, different words.
  • Our detector: 97-100% of the same lines, both times. Rewording barely moves meaning, and meaning is what we compare.
  • Alert volume on one clean day: Wazuh 4,546 alerts, us 1,415 incidents — for 9 real attacks. Both far too many. That is analyst fatigue, measured on both sides.

Sources: CLAUDE.md Decision Log 2026-08-18; results/bakeoff/bakeoff.md; results/killpoint/killpoint_ambient0.05.md.

Problem Statement

  • SIEM rules match the text of a log line, not its meaning — so an attacker who simply rewords an attack walks straight past them.
  • And nobody reports how much detection is actually lost when the attacker is deliberately hiding, so the size of the problem is unknown.
Department of Computer Engineering | SJCEM    5

Motivation

  • Analysts drown in alerts. On one clean corpus a production SIEM raised 4,546 alerts for 9 real attacks. Alert fatigue is not a talking point; it is measurable.
  • Words change, behaviour does not. An attack keeps its shape — many failures from one place, a login from two countries an hour apart — even when the wording changes. Meaning-based detection can follow that; string matching cannot.
  • It has to run where the budget is. The whole system runs on an ordinary laptop with no GPU and no cloud account. A GPU only speeds the written explanation up (5.2 s vs 24.2 s per incident). A team with no security budget can still deploy it.

Objectives

  • Parse raw Linux system and authentication logs into a clean, structured form.
  • Detect anomalies from the meaning of a log line, using sentence embeddings and a per-user Isolation Forest, with no labelled training data.
  • Group related anomalies into a single incident and attach the matching MITRE ATT&CK technique from a lookup table, never from the language model.
  • Explain each incident in plain English with a local LLM that runs offline.
  • Measure the system and a production SIEM (Wazuh) on the same logs, under eight camouflage strategies, and report the difference — including where we lose.
  • Keep the whole system running on a laptop with no GPU and no cloud service.
Department of Computer Engineering | SJCEM    10

Proposed Methodology

  • Read logs → parse and mask → embed the meaning → score each user → group into incidents → attach MITRE technique → explain in English → show the analyst.
  • Camouflaged attacks are fed back in and both systems re-scored on every change.
  • Isolation Forest over embeddings is standard; we do not claim it as the novelty. The measurement is the contribution.
Department of Computer Engineering | SJCEM    11

System Architecture

  • Three live sources — a tailed file, this machine's journal, or a paced replay.
  • The model is fitted once on history and only scores the stream after that.
  • Streaming produces exactly the batch result: 751 lines → 130 events → 94 incidents.
  • The Wazuh comparison track is a separate package the pipeline may never import.
Department of Computer Engineering | SJCEM    12

Implementation: keeping the comparison fair

  • One writer appends every line to both systems in the same call — neither can be handed different traffic.
  • Our injector wrote the attack, so every line's label is recorded as it goes out: ground truth is automatic.
  • The same scoring code grades both systems.
  • Built so far: foundation and 449 tests · benchmark platform with a real SIEM · live streaming, API and dashboard · the live bake-off.

Results

Robustness (5 seeds, real OpenSSH logs, both systems on the same corpus). The number is the drop in detection when the attack is camouflaged: bigger is worse.

Camouflage Us Wazuh Difference
Reworded (rephrase) −2.2 −33.3 +31.1 in our favour
Mimicry / noise / volume / timing 0.0 0.0 tie ×4
IP rotation −11.1 0.0 −11.1 against us
Slowed down −8.9 0.0 −8.9 against us
Realistic combination −13.3 0.0 −13.3 against us

Result: 1 win, 4 ties, 3 losses. The registered threshold (≥25 points on at least one strategy, written into git before we had any result) is cleared by rewording, so the project continues — but the honest claim is narrow: signature rules break when you reword an attack; embeddings do not.

Live demonstration of the same effect (results/bakeoff/bakeoff.md, 18 conditions): rewording an impossible-travel attack took Wazuh from 3 of 3 instances to 0 of 3, while we stayed at 3 of 3 — a 100-point gap, live.

Where we are weaker, stated by us: precision 0.29 — 94 incidents raised for 9 real attacks. Impossible travel is caught by a distance-over-time rule, not by the embeddings. IP rotation, slowing down and the realistic combination all beat us and not Wazuh. Fixing precision is the next stage of work.

Working system

Technologies and Resources

Software

  • Python 3.11+, managed with uv
  • sentence-transformers (all-MiniLM-L6-v2) — turns a log line into a vector of its meaning
  • scikit-learn Isolation Forest — flags the unusual ones, one model per user
  • Ollama + phi3 — local LLM for the written explanation. No cloud, no API key
  • Wazuh 4.9 manager in Docker — the third-party SIEM we are compared against
  • FastAPI (service and live feed) · Streamlit (dashboard) · pytest (436 tests) · GitHub Actions

Data

  • LogHub OpenSSH (655,147 real lines, contains real internet attacks) — primary
  • LogHub Linux (parses at 99.4% after our parser fix) — companion
  • 751-line synthetic corpus with full ground truth — regression testing

Hardware

  • Minimum, and fully supported: any laptop, no GPU, 8 GB RAM
  • Optional: NVIDIA GPU, which only speeds up the written explanation (5.2 s vs 24.2 s)
  • Demonstration setup: two laptops, one attacking and running the SIEM, one detecting
